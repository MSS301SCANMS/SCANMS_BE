# Thịnh — Product, Store, Livestream, Voucher

Implemented from `SCANMS_Team_Assignment.docx` and the SCANMS conceptual model. No new microservice or shared database was introduced.

## Business flow

- `POST /api/v1/store-applications` derives the applicant from the authenticated User Service profile. The client cannot choose applicant, status, reviewer, or review times. Manager/admin calls `/{id}/approve` or `/{id}/reject`. Approval creates one approved Store and grants `SHOP_OWNER` via User Service and Keycloak. If role grant fails, the Product Service transaction rolls back. The applicant needs a refreshed Keycloak token to see the new role in the FE.
- Manager/admin can suspend or activate a Store. Product, Variant, Image, and Livestream mutations require the approved Store owner or admin. A suspended owner can still read their dashboard. `GET /api/v1/stores/{id}/dashboard` includes rating, product/livestream/order counts and paid revenue; Order Service owns the underlying `GET /api/v1/store-sales/{id}` aggregate and checks Store ownership independently.
- ProductCategory is manager-managed. Product uses `attributes` and `sizeGuide` JSON; Variant owns SKU, size, color, price, and stock; ProductImage owns object key, URL, primary flag, and sort order. Legacy `sizesStock` and `imageRefs` in Product are ignored on create and update. Checkout uses Variant stock/price, never Product legacy JSON.
- `DELETE /api/v1/product-categories/{id}` completes Category CRUD for managers. Deletion returns a conflict while a product or child category still references the category.
- Feedback creation derives customer ID from the signed user profile and verifies the OrderItem → SellerOrder → Order chain, product ID, seller Store, customer ID, paid Order status, and delivered/completed seller status through Order Service. One feedback per OrderItem/customer is enforced by a database constraint, including hidden/removed feedback. The author can edit an active review via `PATCH /api/v1/feedbacks/{id}` or remove it via `DELETE /api/v1/feedbacks/{id}`; managers can still hide/remove reviews and inspect hidden reviews. Only active feedback contributes to Store rating and public lists.
- Livestream creates as `SCHEDULED`, can transition to `LIVE` then `ENDED`, validates product IDs belong to the Store, and verifies collaborator IDs are approved in Promotion Service. Checkout carries and verifies `sourceLivestreamId`; LIVESTREAM vouchers only discount lines with matching verified attribution.
- Livestream updates can change description, participant references, and collaborator references while the session is open. `GET /api/v1/livestream-sales/{livestreamId}` is owned by Order Service: it checks the signed user's active profile and Store ownership, then counts distinct buyers/orders, sold quantity, GMV before discounts, and net sales after discounts from paid attributed OrderItems. Cancelled seller orders and unpaid/cancelled/expired master orders do not contribute. Returns after delivery are not subtracted from GMV.
- Voucher creation validates issuer ownership, scope references, validity, whole-VND fixed discounts, integer usage limits, and funding. Codes are unique and canonical uppercase. Checkout uses `PLATFORM`, `STORE`, or `SHARED` funding values expected by Order Service. Reservations create a `RESERVED` VoucherRedemption; commit requires a matching reservation/redemption and marks it `USED`; release before commit marks it `CANCELLED`. A committed voucher cannot be released; `POST /api/v1/checkout-vouchers/{orderId}/restore` marks a used redemption `RESTORED` only after Order Service confirms cancellation before delivery. Post-delivery returns do not automatically restore usage.

## Integration notes

- Product Service calls User Service on port 8081, Order Service on port 8083, and Promotion Service on port 8085. Promotion calls Product Service on port 8082 and User Service on port 8081. Configure `USER_SERVICE_URL`, `PRODUCT_SERVICE_URL`, `ORDER_SERVICE_URL`, and `PROMOTION_SERVICE_URL` when changing ports.
- Gateway routes `/api/v1/livestream-sales/**` and `/api/v1/store-sales/**` to Order Service. The FE resource detail panels call those routes through its `/api/v1` Vite proxy; shop and livestream metrics require the signed Store owner or ADMIN.
- Order's generic SellerOrder/Shipment status writes now require ADMIN or ORDER_INTERNAL, and return decisions require ADMIN, MANAGER, or ORDER_INTERNAL. Seller decisions need a separate ownership-aware policy before enabling them. This keeps buyers from manufacturing a delivered order or approving a return through these generic endpoints.
- Order's resource-finalization worker calls Voucher commit/release only when the persisted checkout request contains a voucher code. Voucher commit now rejects missing reservations, so orders without vouchers must skip that command. Product, Order, and Promotion exception handlers preserve business HTTP statuses instead of turning them into 500 responses.
- The Keycloak client configured for User Service must be allowed to read realm roles and assign `SHOP_OWNER`. Manager/admin tokens must have the corresponding signed realm role. The new role appears in the applicant's next Keycloak access token.
- The explicit voucher restoration endpoint is available for the Order cancellation workflow; the current Order Service has no customer cancellation command to call it automatically. Its eligibility read endpoint is `GET /api/v1/orders/{id}/voucher-restoration-eligibility`.
- Cross-team authorization still needs work in Order Service: generic GET list/detail routes for Orders, SellerOrders, OrderItems, Shipments, and Returns currently require a JWT but do not consistently check customer or Store ownership. FE filtering is presentation only. Review these routes with the Order/Auth owners before using real customer data.
- Added unique constraints for Store owner, Voucher code, VoucherRedemption order, and Feedback OrderItem/customer. Existing PostgreSQL rows should be checked for duplicates before updating a populated database.
- Product Service's Docker PostgreSQL uses `CATALOG_DB_NAME` and `CATALOG_DB_PORT` like its Spring configuration. This avoids the machine's local PostgreSQL on port 5432. The local smoke test ran User, Product, Order, and Promotion Java services against PostgreSQL/Keycloak containers and verified StoreApplication approval plus Keycloak SHOP_OWNER grant, Product/Variant creation, Livestream start/stats, Livestream voucher creation, Order-backed buyer/GMV and Store revenue summaries, verified Feedback create/edit/remove with rating recalculation, and suspended Store read/write permissions. The sales test used a synthetic paid Order through the ADMIN internal API; payment, full checkout, voucher commit/restore after a real payment, and AI analysis still require their own live integration checks and service/provider credentials.
